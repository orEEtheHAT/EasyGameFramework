# Снимки ресурсов и активных операций

EasyResources владеет состояниями ресурсов и операций. EasySave оркестрирует слоты, версии контейнера сохранения, I/O и участников загрузки. У ресурсного модуля нет собственного файлового сервиса или глобального игрового цикла.

## Проверка до изменения мира

В `EasyResources.Runtime`, namespace `EasyResources`:

```csharp
ResourceRestoreReport ResourceStore.ValidateState(
    ResourceContainerState state,
    IEnumerable<ResourceDefinition> definitions,
    ResourceRestoreOptions options = default);
```

`ResourceContainer` предоставляет такой же вызов через свой Store. Фасад компонента доступен в Play и использует обычную ленивую инициализацию Store, если он ещё не был создан. Для строгой проверки уже существующего состояния используйте сохранённую ссылку на ResourceStore; для Edit-time настроек компонента — `ValidateConfiguration()`.

ValidateState и RestoreState используют один PrepareState: проверяют формат, ID/точность, дубли, отрицательные количества, вместимость/вес/объём/фильтры, политики активных операций, суммы резервов, владельцев, время и переполнение. Неверные данные вызывают те же исключения. На readonly replica authoritative restore запрещён. Проверка выполняется на создающем потоке и отклоняется внутри уведомления участника ещё до перечисления каталога.

Успех возвращает планируемые `IgnoredResourceCount` / `RestoredReservationCount`. Балансы, ревизия, журнал, подписки, поколения handles и ожидающие области уведомлений не изменяются. DTO и SO не переписываются. Это не scratch Restore: создаются только отделённые проверочные структуры. Метод предназначен для загрузки и выделяет память. Если данные, правила или живое состояние изменились после проверки, RestoreState обязан проверить их заново.

## Простой кошелёк

По умолчанию `CaptureState()` и восстановление запрещают активные резервы. Это удобный маршрут для полностью завершённых операций. `CaptureState` и `ResourceReplicator.Capture` также запрещают открытый короткий `ResourceNotificationScope`: снимок делается после завершения синхронной команды, а не посреди её уведомлений.

Обычный state содержит версию DTO, стабильные ID ресурсов, точность, количества и ревизию. Он независим от живого хранилища. `UnknownResourcePolicy.Reject` — стандарт; Ignore может пропустить неизвестный обычный остаток, но никогда не выбрасывает часть зарезервированной стоимости. Определения остаются конфигурацией проекта и разрешаются по ID.

## Возобновление именованных резервов

Сохранение активных операций требует явного протокола приложения:

1. При создании длительной операции задать `ResourceReservationOptions(ownerId, ..., nowMilliseconds)`. OwnerId постоянен и не пуст; он связывает операцию с резервом, но не является сетевой аутентификацией.
2. В одном синхронном участке захватить **все кошельки и их владельцев**: `CaptureState(includeReservations: true, nowMilliseconds: now)`, фазы операций, reservation ID, OwnerId, замороженные оставшиеся стоимости, времена и относящиеся к результатам состояния. Затем передать независимый DTO асинхронному I/O EasySave. Сам Unity snapshot не является фоновой задачей.
3. При загрузке остановить новые команды и автоматическое продвижение восстанавливаемых операций. Проверить всю доступную структуру игрового DTO и кошельки через ValidateState. Использовать `ResourceRestoreOptions(resumeReservations: true, replaceActiveReservations: true, nowMilliseconds: newNow)`.
4. Сначала восстановить кошельки. `ResourceSnapshots.RestoreAll(stores, states, definitions, options)` проверяет всех участников до записи и публикует события после установки всех их состояний. Старые holds/scopes инвалидируются только на успешном применении; прежние pending notifications отбрасываются.
5. Затем восстановить владельцев. Пользовательская операция использует `TryGetReservation(savedId, ownerId, out hold)` и сверяет `CopyRemainingTo` с сохранённой стоимостью. **Не вызывает повторно TryReserve**. Completed-фаза не повторяет commit или выдачу результата.
6. Сопоставить каждый восстановленный резерв ровно одному владельцу, явно отменить брошенные операции, затем разрешить команды и Tick. Два владельца одного hold могут неправильно управлять одной оплатой; idempotent commit не заменяет проверку владения.

## Готовые владельцы операций

| Состояние | Восстановление после кошельков | Граница |
|---|---|---|
| ProductionQueueState | `ProductionQueue.FromState(source, destination, state, recipes, resources, now, capacity, offlineMilliseconds)` | Проверяет OwnerId, reservation IDs и замороженные Inputs; не создаёт повторный резерв. Tick выполняется отдельно и может остановиться на ограничении места для Outputs. |
| ProductionStation | `station.RestoreState(state, recipes, resources, offlineMilliseconds)` | Заменяет прежнюю очередь только после успешного создания новой. Нужен предварительный restore её кошельков. |
| ProgressionState | `ProgressionProfile.FromState(definition, restoredWallet, state, resources, now, offlineMilliseconds)` | Возвращает новый профиль с сохранёнными рангами/XP/исследованием. Проверяет owned hold и frozen cost. Завершение исследования — отдельная операция. |
| ProgressionComponent | `component.RestoreState(state, resources, offlineMilliseconds)` | Сначала кошелёк, затем профиль. Старые владельческие handles не могут отменить восстановленные резервы. |
| ResourceDeliveryState | `ResourceDelivery.FromState(source, destination, state, definitions, now, offlineMilliseconds)` | Возобновляет сохранённый груз по тому же резерву; доставка/списание выполняется позднее явно. |
| InventoryState | `inventory.RestoreState(state, items, now, offlineMilliseconds)` | Полная замена инвентаря после проверки; снимок не содержит незавершённой оплаты. `TryCraft` — синхронная атомарная операция кошелёк + инвентарь. Отложенное производство принадлежит ProductionQueue. |

У FromState есть собственная полная проверка связанных данных. Они не являются общим немутирующим preflight всего мира: требуют уже восстановленные кошельки и новые handles. ResourceStore.ValidateState проверяет **кошелёк**, а не чужую фазу операции или будущую вместимость всех результатов.

RestoreAll атомарен только относительно перечисленных ресурсных хранилищ. Если последующий restore очереди/профиля/другого модуля отклонён, мир уже может быть частично загружен. EasySave должен показывать PartialRestore/ошибку и оставлять управление восстановлением вызывающей системе. Нельзя объявлять такой результат полной транзакцией мира, автоматически отменять чужие восстановленные holds или скрывать ошибку повторной оплатой. Повтор загрузки начинается со всего согласованного снимка, включая кошельки, а не только с failed owner.

Исходные SO не хранят баланс, опыт, ранг, содержимое слотов или фазу задачи. Для будущих изменений точности/ID есть явные преобразования данных; переименование существующего asset не меняет его ID.
