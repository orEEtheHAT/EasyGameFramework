# Ресурсная награда

Создайте **Create → EasyGameFramework → Resources → Resource Reward** Назначьте **Database** и добавьте строки в Rewards. Ресурсы выбираются поисковым списком только из этой базы; их параметры редактируются в Resource Database. Каждая строка содержит Resource, Min и Max. Все перечисленные ресурсы входят в награду.

Например, для целочисленных Coin и Crystal задайте Coin **3–7**, Crystal **1–3**. Каждая граница включена: возможны 3 и 7 монет, 1 и 3 кристалла. **Min = Max** даёт фиксированное количество; **0–0** ничего не выдаёт. Пустой профиль — допустимая пустая награда.

Инспектор показывает обычные количества с точностью выбранного Resource. При Decimal Places = 2 диапазон **1,25–1,27** означает три варианта: 1,25 / 1,26 / 1,27. Внутри хранятся точные целые наименьшие единицы: 125 / 126 / 127. Пределы не округляются, отрицательные значения и лишняя дробная точность отклоняются. Используется системный десятичный разделитель.

## Розыгрыш и выдача

```csharp
using EasyResources;

ResourceCost rolled = rewards.Roll(); // Один раз на событие награды.
bool granted = wallet.TryGrant(rolled, out ResourceFailure failure);
// wallet — ResourceContainer или ResourceStore.
```

Все строки выдаются атомарно. Если хотя бы одна не помещается по количеству, весу, объёму или фильтру, либо возникло переполнение, TryGrant возвращает false и ResourceFailure; ни один ресурс не зачисляется. При успехе наблюдатели получают один согласованный Changed, а DetailedChanged — строки окончательной выдачи. Обычные правила main thread, reentry и уничтожения контейнера сохранены.

При отказе сохраните `rolled` и повторите **TryGrant с тем же результатом**, когда решите проблему. Повторный Roll создаст другую награду. Сам TryGrant не хранит paid-флаг: каждый успешный вызов означает новую выдачу. Вызывающая механика контролирует, что событие обработано один раз, и как это состояние сохраняется. Боевой адаптер смерти принадлежит интеграции EasyCombat → Resources.

```csharp
var context = new ResourceOperationContext("reward", operationId);
if (wallet.TryGrant(rolled, out var failure, context))
    CompleteRewardOperation();
else
    KeepPendingReward(rolled, failure); // Явная политика вызывающего кода.
```

SO хранит только список диапазонов. Он не сохраняет последний бросок, деньги, получателя или фазу оплаты. Несколько врагов могут использовать один профиль, сохраняя отдельные результаты. Последующие Roll не меняют предыдущий ResourceCost или сериализованные данные профиля/Resource assets.

## Создание из кода и воспроизводимость

```csharp
// database — явно назначенная ResourceDatabase, содержащая coin и energy.
var profile = ResourceRewardProfile.Create("Reward", database,
    new ResourceRewardRange(coin, 3, 7), // Конструктор принимает RAW units.
    ResourceRewardRange.FromQuantity(energy, 1.25m, 1.75m)); // Обычные точные количества.

var random = new System.Random(1729);
ResourceCost rolled = profile.Roll(random);
```

Созданный в runtime профиль — Unity-объект, его освобождает создавший код. Для обычной настройки используйте сохранённый asset. `Ranges` предоставляет read-only список, а `ValidateConfiguration()` проверяет весь профиль без розыгрыша или изменения состояния. Сохранение asset из Editor выполняется стандартным AssetDatabase.CreateAsset.

По умолчанию используется UnityEngine.Random; можно передать свой System.Random для seed/тестов. Seed относится к потоку RNG: фиксированные строки его не расходуют, переменные расходуют по мере розыгрыша. Это не обещание одинаковых результатов между версиями разных RNG/backend. Пользовательский Random обязан соблюдать стандартный контракт Next(maxValue).

Повторяющиеся строки **одного Resource asset** разыгрываются независимо, затем складываются. Две строки 1–2 отличаются по распределению от одной 2–4. Сумма **максимумов** дубликатов должна помещаться в long; ошибочная конфигурация отклоняется до первого случайного вызова. Разные assets с одним стабильным ID тоже отклоняются. Отсутствующие ссылки, неверные определения, Min > Max, отрицательные количества и переполнение не дают частичной выдачи.

Диапазон поддерживает весь неотрицательный Int64, включая **0–long.MaxValue**. Равномерный выбор выполняется целыми битами с отбрасыванием лишнего хвоста; float-масштабирования и вычисления `long.MaxValue + 1` нет. NaN/Infinity отсутствуют в типе long/decimal и отклоняются при вводе в инспекторе.

## Производительность и проверки

У профиля нет Update, таймера, подписок или поиска получателя. Roll создаёт независимый ResourceCost и вспомогательные структуры **при событии**; это выделяющая память операция. Подготовленный результат можно передавать TryGrant повторно: существующие буферы транзакции переиспользуются, после прогрева выдача не создаёт managed allocations. Создание asset/стоимости и расширение вместимости относятся к подготовке.

Проверено на Unity 6000.3.22f1 в Games Factory: **22 новых EditMode + 2 новых PlayMode**, весь модуль **160/160 EditMode и 13/13 PlayMode**. В тесте выделений 64 прогревочных выдачи, затем 256 измеряемых выдач двух ресурсов дали **0 GC.Alloc событий**; положительный контроль `new byte[1024]` зарегистрирован. Это результат Editor-теста ядра; Player/полный death adapter сюда не входят.

Отчёты: [Rewards-20261116](Reports/Rewards-20261116/Validation.md). Смерть/возрождение, одна награда на жизнь врага и обновлённый Playground проверяются владельцами Combat и общего стенда через опубликованный контракт.


Профиль требует Database даже для пустой награды. Setter Database проверяет существующие строки до смены привязки; чужая база отклоняется без изменения строк. Смена поля в Inspector сохраняет старые ссылки и показывает ошибку, пока вы явно не выберете допустимые ресурсы. Одинаковый ID другого объекта не означает членство в базе. [Редактирование базы](ResourceDatabase.md).
